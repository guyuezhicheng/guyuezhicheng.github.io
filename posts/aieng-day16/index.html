3.1 SafeJIT：把带 JIT 的可执行文件验证到机器码级，编译器和链接器都不信任

  1. 出处：arXiv:2611.28436，v1 2026-11-21，cs.PL；Gabriel Ebner（单一作者）。abs 页未印机构，不臆断。预印本，未经同行评审、待复现；结论限论文给出的 Linux 用户进程模型与 Sail ISA 模型。
  2. 做了什么：做了一个带推测式 baseline JIT 的小型 JavaScript 引擎 SafeJIT，并在 Lean 4 里给出机器检查的证明：它在任意输入下、静态链接生成的 RISC-V 和 x86-64 可执行文件都不会崩。定理针对“交付出去的那个二进制”，在 Sail 指令集模型（RISC-V 用官方模型）上逐条指令执行，覆盖解析器、字节码编译器、解释器、JIT 生成的全部机器码（类型守卫、守卫消除、内联缓存、反优化、栈上替换）、标记清除 GC、运行时和一个独立 libc。C 编译器、汇编器、链接器都不被信任，浮点运算也不被信任。证明用分离逻辑（iris-lean），把“进程卡死”精确定义为崩溃的各种方式，包括取到未标记为可执行的指令、指令缓存未刷新。
  3. 改变了哪个旧假设：推翻“链接器、C 编译器是可信基座，形式化验证只能证明到源码或 IR 层”。它把信任边界一直推到最终交付的机器码，连链接产物本身都在定理范围内——你链接出什么，我就验证什么。
  4. 意义：给高攻击面组件（JIT）一个端到端的、落到 shipped binary 的正确性保证；也说明构建工具链不是必须信任的黑盒。
  5. 关联今天：你今天用 ld 把 add.o/sub.o/mul.o 链成一个可执行文件，默认假设“链接器干得对”。SafeJIT 研究的就是这个假设能不能拿掉：它对静态链接产物逐指令验证，且明确不信任链接器。今天记住一件事——你 make 出来的 app 是链接器拼出来的，不是一个源文件变出来的；理解这层，才看得懂“为什么静态库的代码会拷进二进制、动态库不会”。这是作者自述的机器证明结果，待独立复现。

3.2 Pudding：把“架构描述”做成编译流水线的一等对象，换目标只喂描述

  1. 出处：arXiv:2611.30446，v1 2026-11-23，cs.AR / cs.ET；Tianrui Zheng、João Paulo Cardoso de Lima、Alexander Kusnezoff、Asif Ali Khan、Jeronimo Castrillon。abs 页未逐作者印机构，不臆断。预印本，未经同行评审、待复现；性能为作者在多个 PUD 目标上的实测自报。
  2. 做了什么：面向 PUD（Processing-Using-DRAM，利用 DRAM 阵列物理特性直接在内存里做布尔运算）的可重定向端到端编译框架。此前多个 PUD 架构的原语集、行分配模型、执行指标各不相同，差异被硬编码进各自的编译器，跨架构复用不可能。Pudding 的核心是把“架构描述”变成编译流水线里的一等对象：换一个新 PUD 架构，只要提供它的描述，不改编译器。框架建在 MLIR 上、分两层：张量层用位切片、混合精度分配、ILP 布局减少 PUD 命令和跨 bank 数据搬运；逻辑层用 equality saturation 探索布尔网络实现，重写规则和代价函数都直接从架构描述导出。用同一套编译 pass 跨多个 PUD 目标，匹配甚至在部分场景超过为特定架构手写的优化编译器。
  3. 改变了哪个旧假设：推翻“目标架构的差异必须硬编码进编译器、换架构就得重写一套编译链”。配置/描述本身可以是一等输入，编译器主体不动。
  4. 意义：可重定向编译的成本从“重写编译器”降到“写一份描述”，跨架构复用和扩展成为可能。
  5. 关联今天：你今天写的 Makefile 和 CMakeLists.txt，本质就是把“构建配置”从源码里抽出来变成一等输入——同一批 add.c/sub.c/mul.c，改配置就能产出“直接链接版 / 静态库版 / 动态库版”三种可执行文件，源码一个字不用改。Pudding 把这个思想推到编译器内核：架构描述就是配置。理解“配置驱动同一批源码产出不同目标”，你就抓住了 Makefile/CMake 与可重定向编译的共同内核。作者自报的性能数据待独立复现。

4. 新知讲解：多文件编译、静态库/动态库、Makefile/CMake

4.1 为什么要拆文件

  1. 一个 .c 文件就是一个编译单元：gcc -c add.c 只编译它自己，产出 add.o，此时不知道 sub、mul 在哪。
  2. 拆开的好处：改一个文件只重编一个 .o；多人各写各的；函数实现可以打包成库给别人用。代价是必须解决“跨文件怎么知道对方有这个函数”。
  3. 解决办法就是声明与定义分离：.h 里放函数原型（ declaration，只说签名，不产生代码），.c 里放函数体（ definition，产生代码）。别的 .c #include 这个 .h，编译器就知道去哪找符号，链接器最后把 .o 拼起来时再对上号。
  4. 头文件为什么不能放定义：如果 add 的函数体写进 mathkit.h，被 4 个 .c 各 include 一次，就产生 4 份 add 定义，链接时报 multiple definition。头文件里只允许放声明、#define、类型定义这类“不产生实体代码”的东西（D15 的 include guard 防止的就是同一编译单元内重复 include）。

4.2 编译四步走到链接：从源文件到可执行文件

  1. 回顾 D15 的四步：预处理 → 编译 → 汇编 → 链接。拆多文件后，前三步对每个 .c 各自跑一遍，各生成一个 .o；最后链接器把若干 .o 加库合成一个可执行文件。
  2. 手动走一遍（在 day16/ 目录下）：
    • gcc -std=c11 -Wall -Wextra -fPIC -Iinclude -c src/add.c -o src/add.o（sub.c、mul.c、main.c 同理）
    • gcc src/main.o src/add.o src/sub.o src/mul.o -o app
    • ./app 看输出。
  3. -Iinclude 告诉编译器去 include/ 找 "mathkit.h"；不加就报 mathkit.h: No such file or directory。
  4. .o 是目标文件：里面有机器码，但函数地址还没最终确定（对别的 .o 里符号的引用是“待填的坑”）。链接器的活就是填这些坑、分配最终地址。用 nm src/add.o 能看到 add 这个符号是 T（在 text 段有定义），nm src/main.o 里 add 是 U（undefined，等别人提供）。

4.3 最小示例代码（day16/min.c，完整可直接编译）

单文件把“声明”和“定义”摆一起，先看懂原型的作用，再去 3.4 看真实的拆文件版：

/* day16/min.c - 最小示例：一个函数放头文件（错）vs 放 .c 分开编译（对）
 * 这个文件演示“声明放 .h、定义放 .c”，单文件即可编译运行。
 * 编译：gcc -std=c11 -Wall -Wextra day16/min.c -o day16/min && day16/min
 */
#include <stdio.h>

/* 声明（原型）：只告诉编译器签名，不产生代码 */
int add(int a, int b);
int mul(int a, int b);

/* 定义：真正产生代码；在真实工程里这两段在 add.c / mul.c */
int add(int a, int b) { return a + b; }
int mul(int a, int b) { return a * b; }

int main(void)
{
    printf("add(2,3)=%d\n", add(2, 3));
    printf("mul(4,5)=%d\n", mul(4, 5));
    return 0;
}

编译运行：gcc -std=c11 -Wall -Wextra day16/min.c -o day16/min && day16/min

期望输出（两行）：

add(2,3)=5
mul(4,5)=20

关键点：main 里能调用 add，靠的是前面那行原型，不是靠函数体写在它前面。把原型删掉、把定义挪到 main 后面，编译器就会警告隐式声明——这就是“声明在前”的意义。真实工程把原型放进 .h，效果一样，只是跨了文件。

4.4 静态库 .a：链接期拷贝

  1. 打包：ar rcs libmathkit.a src/add.o src/sub.o src/mul.o。ar 是归档工具，把多个 .o 装进一个 .a。nm libmathkit.a 能看到里面每个符号。
  2. 使用：gcc src/main.o -L. -lmathkit -o app-static。-L. 说“去当前目录找库”，-lmathkit 说“链接 libmathkit.a”（lib 前缀和 .a 后缀省略）。
  3. 本质：链接器从 .a 里挑出被引用的那些 .o，把机器码整段拷进可执行文件。链接完成后，可执行文件不再需要 .a。删掉 libmathkit.a，./app-static 照样跑。
  4. 后果：每个用这个库的程序都带着一份库代码副本 → 可执行文件体积大、多个程序不共享；库升级了，所有用它的程序都要重新链接。

4.5 动态库 .so：运行期加载

  1. 打包：gcc -std=c11 -Wall -Wextra -fPIC -shared -o libmathkit.so src/add.o src/sub.o src/mul.o。
  2. -fPIC = Position Independent Code（位置无关码）：代码里不写死绝对地址，才能被加载到任意内存位置。这就是 Makefile 里统一给 CFLAGS 加 -fPIC 的原因——同一批 .o 既进静态库又进动态库，不加的话 x86-64 链接 .so 会报 relocation R_X86_64_PC32 ... recompile with -fPIC。
  3. 使用：gcc src/main.o -L. -lmathkit -Wl,-rpath,'$ORIGIN' -o app-shared。-Wl,-rpath,'$ORIGIN' 告诉动态链接器“先去可执行文件所在目录找 .so”，'$ORIGIN' 用单引号防止 shell 提前展开。
  4. 本质：链接期只在可执行文件里记一条“我依赖 libmathkit.so”（用 readelf -d app-shared | grep NEEDED 能看到），代码不拷进来。程序启动时，动态链接器 ld.so 把 .so 映射到进程地址空间。用 ldd app-shared 能看到它找到了哪个 .so。
  5. 后果：多个进程共享磁盘上一份 .so（物理内存也可共享）→ 省空间；.so 升级后所有程序下次启动就用新的，不用重新链接；代价是运行时必须找得到 .so，找不到就报 error while loading shared libraries。

4.6 加载时机差别（今天的核心考点，一句话记牢）

  1. 静态库：链接期（构建时）拷贝代码——库代码进了可执行文件，运行不依赖库文件，体积大，升级要重链。
  2. 动态库：运行期（程序启动时）加载代码——可执行文件只记依赖，运行要找得到库文件，可共享，升级不用重编主程序。
  3. 三条命令各看一个证据：nm libmathkit.a 看静态库里有哪些符号；readelf -d app-shared | grep NEEDED 看动态依赖；ldd app-shared 看运行时到底加载了哪个 .so。

4.7 Makefile：把编译命令写成可重复的规则

  1. 核心结构是一条 rule：目标: 依赖 下一行（必须以 tab 开头）是配方。make app 时，Make 检查 app 比依赖旧或不存在，就执行配方。
  2. 三个自动变量：$@ = 目标名，$^ = 全部依赖，$< = 第一个依赖。写 $(CC) $(CFLAGS) -c $< -o $@ 一条模式规则就能编译所有 .c。
  3. 模式规则 %.o: %.c include/mathkit.h：% 匹配任意名字，src/add.o 匹配出 src/add.c。把头文件列进依赖，改了 mathkit.h 就会重编所有 .o——这就是增量构建的意义。
  4. .PHONY: all app static shared clean 声明这些是“动作名”不是文件名，避免同名文件存在时 make 误判“已是最新”。
  5. tab 是硬要求：配方行用空格缩进会报 missing separator。本工程 day16/Makefile 已用真实 tab。

4.8 CMakeLists.txt：跨平台的构建描述

  1. CMake 不直接编译，它生成当前平台的构建文件（Makefile / Visual Studio 工程等），再由底层工具编译。好处是一份 CMakeLists.txt 跨平台通用。
  2. 常用指令：cmake_minimum_required、project(mathkit C)、set(CMAKE_C_STANDARD 11)、add_library(... STATIC/SHARED ...)、add_executable(...)、target_link_libraries(...)、target_include_directories(...)。
  3. add_library(mathkit_static STATIC ${LIB_SRC}) 和 add_library(mathkit_shared SHARED ${LIB_SRC})：同一批源文件，分别产出静态库和动态库；set_target_properties(... OUTPUT_NAME mathkit) 让两者都叫 mathkit（一个出 libmathkit.a，一个出 libmathkit.so，不冲突）。
  4. CMake 自动给 SHARED 库加 -fPIC，不用手动写。这是它比手写 Makefile 省心的地方。
  5. 构建用 out-of-source：cmake -S . -B build 生成到 build/，cmake --build build 编译，产物不污染源码目录。

7. 检验标准（5 条硬条件，逐条能回答“过没过”）

  1. 三种方式（gcc 手动 app、make 的 app-static/app-shared、cmake 的 app_direct/app_with_static/app_with_shared）都能产出可执行文件，且运行输出逐字一致（version=1、add(7,3)=10、sub(7,3)=4、mul(7,3)=21 四行）。少一种或有任何一行对不上 = 不过。
  2. 不看资料说清静态库与动态库的加载时机差别：静态库链接期拷贝、动态库运行期加载；并各给一条命令证据（nm 看静态符号、readelf -d 或 ldd 看动态依赖）。说反或说不出证据 = 不过。
  3. 指出 Makefile 里 tab、$@ $^ $<、模式规则三处各起什么作用；把某配方行 tab 换成空格能复现 missing separator 并修回来。做不到 = 不过。
  4. day16/build_notes.md 存在，含三种构建命令、三份输出对照、nm/readelf -d/ldd 三条实际输出片段和一句加载时机结论；git log -1 看得到当日 commit。缺一项 = 不过。
  5. 第 5 节第 9 项补档清单逐项有产出或明确缺口记录；week02/retro.md 存在。空着不写 = 不过。
