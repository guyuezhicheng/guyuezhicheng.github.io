3.1 Strict Capabilities with a PNVI Escape Hatch

  1. 出处：arXiv:2611.20564 [cs.PL]，v1 2026-11-16。作者 Yihe Li、Sai Dhawal Phaye、Roland H. C. Yap、Trevor E. Carlson、Gregory J. Duck，HTML 首页 Affiliation 均印 National University of Singapore（新加坡国立大学）。链接 https://arxiv.org/abs/2611.20564 。22 页，预印本，未经同行评审、待复现。
  2. 做了什么：把 C 指针拆成两套可互操作的抽象。一套是“严格 capability”，同时强制来源（provenance）、存活、类型正确、对象及子对象边界；另一套是“exposed representation”——不可解引用、整数样的值，按 PNVI（Provenance Not Via Integers）语义允许任意整数/字节级操作，但不携带任何可直接访问内存的权限，转回严格 capability 时才重建 provenance 并校验类型与边界。用 Fully Randomized Pointers（FRP）+ 动态类型元数据分析实现，在指针惯用法、Juliet 测试集和既有 C benchmark 上评估。
  3. 改变了哪个旧假设：过去默认“一套 capability 抽象必须在宽松和严格之间二选一”——要不放松以兼容 C 的整数/字节技巧，要不收紧以堵类型混淆和越界。本文证明两套抽象并存可行：普通指针派生保持严格，只有显式“逃生舱”才进入宽松域。
  4. 意义与今天的关联：capability 的核心就是“指针带着它是从哪块分配来的信息”。今天你区分 char arr[]（来源=栈，可写）和 const char *p（来源=.rodata，只读），正是最朴素的 provenance + 边界判断。D11 的 ASan 是给堆分配加运行时红zone，和这篇是同一条线上的软硬两端。

3.2 CHERI under Fault Injection

  1. 出处：arXiv:2611.19915 [cs.CR] / [cs.AR]，v1 2026-11-15。作者 Eva Sophia Schreyer，abs 页 comments 标明是提交给 KTH Royal Institute of Technology（瑞典皇家理工学院）的硕士论文。链接 https://arxiv.org/abs/2611.19915 。预印本，未经同行评审、待复现。
  2. 做了什么：CHERI 给每个指针附加硬件校验的元数据，强制空间的和时间的内存安全，但其威胁模型明确排除故障注入。本文在基于 QEMU 的模拟环境里实现故障注入原语，注入两类故障——位翻转破坏 capability 元数据、故障诱导跳过 capability store 的检查——演示了缓冲区溢出、控制流劫持、纯数据攻击、use-after-free 四种场景，每个只须一到两个针对性故障（模拟环境下的下界）。
  3. 改变了哪个旧假设：过去倾向认为“指针带上硬件校验的元数据就够安全”。本文指出 CHERI 的保证依赖三件事：元数据的物理完整性、校验指令的不间断执行、revocation bitmap 的完整性；单个针对性故障就能绕过空间安全、时间安全或控制流完整性。同时也写明 CHERI 仍抬高了攻击成本（故障注入是前提，sentry 机制迫使攻击者额外供一个合法带 tag 的 capability 或再花一次故障恢复 tag）。
  4. 意义与今天的关联：元数据（指针从哪来、能访问多大范围）是内存安全的地基，但地基本身也要被保护。这正好落到今天的内容——先把 .data / .bss / .rodata / 栈 / 堆各段在哪、权限如何搞清楚，才谈得上保护它们。今天手绘的布局图就是这张“地基地图”。

4. 新知讲解（讲透 + 最小可运行示例）

4.1 一个 C 程序的内存分成哪几段

从低地址到高地址，典型布局（具体顺序依平台/链接脚本而变，看板只认“同段相邻、段间分散”这个现象）：

  1. 代码段 .text：机器指令，只读。
  2. 常量段 .rodata：字符串字面量、const 全局初值，只读。
  3. 全局/静态区：已初始化的在 .data（如 int g_init = 7;、static int s = 9;），未初始化或初值为 0 的在 .bss（如 int g_zero;，操作系统加载时清零，不占可执行文件体积）。程序运行期一直存在。
  4. 堆区 heap：malloc / calloc / realloc 申请，程序员手动 free，不释放就泄漏。增长方向通常是向高地址。
  5. 栈区 stack：局部变量、函数参数、返回地址。函数调用时自动分配、返回自动回收，通常向低地址增长。递归爆栈就爆在这。

一句话记：谁分配、谁释放、活多久——栈自动对自动，全局静态程序全程，堆手动对手动，常量只读归编译器。

4.2 字符串的本质

  1. C 没有 string 类型。字符串就是一段 char 数组，约定用 '\0'（字节值 0）标记结尾。"abc" 在内存里其实是 4 个字节：'a' 'b' 'c' '\0'。
  2. 所以 sizeof("abc") == 4，strlen("abc") == 3——前者数字节含结尾符，后者数字符不含。
  3. 数组忘记以 '\0' 收尾，strlen / printf("%s") 就会一路读下去越过数组边界，这是无数漏洞的源头（D11 的 ASan 会抓这类）。

4.3 两种写法，差别全在“来源”

  1. char arr[] = "abc";：在栈上开 4 字节，把字面量内容拷一份进来。这是你的数组，arr[0] = 'X' 合法。
  2. const char *p = "abc";：p 这个指针变量本身在栈上（8 字节），它指向的是 .rodata 里的字面量本体。写 p[0] = 'X' 是未定义行为——那段内存标了只读，通常直接段错误（SIGSEGV）。加 const 就是让编译器在编译期拦住你。
  3. sizeof(arr) 是 4（整个数组），sizeof(p) 是 8（一个指针）。这跟 D9 的“数组退化”是同一件事：数组名在多数表达式里退化成指向首元素的指针，只有在 sizeof 和 & operands 里保持“整个数组”的身份。
  4. 字符串字面量为何不可改：多个 const char *p = "abc"; const char *q = "abc"; 里的 "abc" 通常是同一份只读数据（编译器可能合并），改它等于改别处共享的常量，语义上说不通。C 标准明确规定修改字符串字面量是未定义行为。

4.4 最小可运行示例（落盘在 day10/min.c，一份文件跑完全部现象）

/* D10 min.c -- one file: 4 storage classes + string two spellings */
#include <stdio.h>
#include <stdlib.h>

const char *ro_str = "rodata literal";   /* literal: read-only segment */
int g_init = 7;                          /* global initialized: .data */
int g_zero;                              /* global zero: .bss */
static int s_init = 9;                   /* static: .data */

int main(void) {
    int stack_var = 42;                  /* stack: automatic local */
    static int s_local = 11;             /* static local: .data */
    char arr[] = "abc";                  /* stack array: writable */
    const char *p = "abc";               /* p on stack, literal in .rodata */
    int *heap = (int *)malloc(sizeof(int)); /* heap */

    if (heap == NULL) return 1;
    *heap = 100;

    printf("stack  &stack_var = %p\n", (void *)&stack_var);
    printf("stack  arr         = %p\n", (void *)arr);
    printf("stack  &p         = %p\n", (void *)&p);
    printf("heap   malloc      = %p\n", (void *)heap);
    printf(".data  g_init      = %p\n", (void *)&g_init);
    printf(".bss   g_zero      = %p\n", (void *)&g_zero);
    printf(".data  s_init      = %p\n", (void *)&s_init);
    printf(".data  s_local     = %p\n", (void *)&s_local);
    printf(".rodata ro_str     = %p\n", (void *)ro_str);
    printf(".rodata p          = %p\n", (void *)p);

    arr[0] = 'A';                        /* array copy on stack: OK */
    printf("arr after edit = %s\n", arr);
    printf("literal        = %s\n", p);

    free(heap);
    return 0;
}

编译运行（有 gcc 的机器）：

gcc -std=c11 -O0 -g day10/min.c -o day10/min.exe
./day10/min.exe

看输出的要点：

  1. &stack_var、arr、&p 三个地址彼此很近且偏高——都在栈上。
  2. malloc 的地址明显离它们远——在堆上。
  3. g_init / g_zero / s_init / s_local 挤在一起且偏低——都在全局静态区。
  4. ro_str 和 p 打印出的地址指向同一片 .rodata（两个字面量内容不同，但都属于只读段，彼此相邻）。
  5. arr 改成 "Abc" 成功，p 指向的 "abc" 纹丝不动。

本机 Windows 当前没装 gcc/clang，三份 .c 已用 pycparser 做 C11 语法解析全部通过；等你装好编译器（或 WSL 里 apt install build-essential）再跑实编译。地址绝对值每次运行会因 ASLR 变动，别去背数字，看“谁和谁近”。
