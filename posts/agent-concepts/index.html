Agent 概念笔记：从 LLM 到 MCP 的一层层拆解

从 AtomCode 的安装按钮开始，一路拆到 LLM、RAG、Skill、Multi-Agent、MCP，把这几个经常混着说的词按层理清楚。

1. 先看全貌

这几个词经常混在一起说，其实它们是一层套一层的：

    subgraph L1["最里面：LLM"]
        A1["大语言模型<br/>只负责想，不负责做"]
    end
    subgraph L2["往外一层：Agent"]

    M2["A2A：Agent 接 Agent 的统一协议"] -.接.-> A3

一句话版本：LLM 给脑子，Agent 给手脚，Multi-Agent 给组织，MCP/A2A 给接口标准。

2. AtomCode：从安装按钮说起

2.1 五种安装方式，区别只是“怎么把软件弄到本地”

方式 具体做什么 适合谁
curl 一键脚本 跑一条命令，自动识别系统和芯片、下载预编译包、配环境变量 大多数人，官方推荐
npm npm install -g，要求本机有 Node.js 18+ 已经在用 Node 生态的人
brew brew install --cask atomcode macOS 用户，方便后续统一升级
源码构建 clone 代码，用 Cargo 自己编译，要求 Rust 1.88+ 要改源码、要最新开发版
下载二进制 去 Releases 手动下压缩包，自己放进 PATH 网络受限、环境特殊

装完跑 atomcode --version，能出版本号就算成了。

2.2 真正的分界线不在安装方式，在“大脑在哪”

这里最容易搞混。安装方式决定的只是客户端装在哪，答案永远是本地。而“云端还是本地”问的是模型在哪算：

  1. 软件本体（手脚）：一定在你电脑上，负责读文件、跑命令。
  2. AI 大脑（模型）：看第 02 步的 provider 配置。
    • 选 DeepSeek / GLM / Qwen：代码发到人家服务器算，要联网，按量付费或用免费额度。
    • 选 Ollama：模型下载到自己电脑跑，断网也能用，数据不出门，但吃显卡。

打个比方：安装方式是“怎么把播放器装进电脑”，provider 是“片子从哪来”——看在线流媒体，还是放本地下载的 MP4。播放器怎么装的，跟片子从哪来没关系。

3. AI、LLM、RAG、Agent 四个词的关系

3.1 LLM：只有脑子的百事通

LLM（Large Language Model，大语言模型）就是 ChatGPT、DeepSeek、GLM、千问这些。它知识多、能推理，但：

  1. 知识停在训练截止那天；
  2. 不知道你的私有代码和内部文档；
  3. 没有手脚，只能输出文字，问一句答一句。

问它“这 bug 怎么回事”，它给你一段建议代码，然后你自己去复制、粘贴、运行。

3.2 RAG：给大脑一本开卷资料

RAG（Retrieval-Augmented Generation，检索增强生成）不是模型，是一套流程：先从外部资料库检索，再把检索结果连同问题一起喂给模型，让它照着资料答。

  • 纯 LLM = 闭卷考试，全凭记忆。
  • LLM + RAG = 开卷考试，允许先翻书再写答案。

检索那一步一般在向量数据库里做（把文档切成片段、转成向量、按相似度找），所以 RAG 常被叫作“外挂知识库”或“长期记忆”。

3.3 Agent：脑子加上手脚，还能自己循环

Agent 是你给它一个目标，它自己拆步骤、调工具、看结果、修正，直到把活干完。你不用告诉它每一步怎么做。

还是修 bug 那个例子：

  1. 只有 LLM：泛泛说“可能少了个分号”。
  2. LLM + RAG：查了内部知识库，告诉你“是上周那个接口改了，改第 20 行”。
  3. LLM + RAG + Agent：查完直接打开你的文件，改了第 20 行，跑了测试，最后报一句“修好了”。

3.4 三者不是并列，是包含

概念 位置 类比
LLM 底层能力 发动机
RAG 让 LLM 少犯错的外挂 导航地图
Agent 把上面这些组装起来干活的系统 整辆自动驾驶汽车

4. 公式进化史

这条线是从你那句总结一步步长出来的。

v1（最初版）

Agent = AI大模型（大脑） + 记忆（上下文） + 工具（读写文件/终端执行） + 规划执行能力（自主循环）

v2（把 RAG 明确写进去）

Agent = LLM（核心大脑） + 上下文记忆（短期） + RAG（检索外部知识/长期） + 工具（手脚） + 规划执行能力（自主循环）

v3（加上 Skill，换成行业正经术语）

Agent = LLM
      + Working Memory / Context Window（短期记忆）
      + RAG（长期记忆）
      + Tools（基础工具）
      + Skills（技能包）
      + Planning（规划循环）

4.1 六个部件分别干什么

  1. LLM：理解指令、做判断。缺了它，剩下全是死代码。
  2. Working Memory / Context Window：当前对话历史、刚调过的工具、刚看到的报错都存在这。窗口满了就得压缩或丢弃，这就是“上下文工程”要管的事。
  3. RAG：补模型不知道的知识。缺了它，模型遇到私有数据就只能瞎猜。
  4. Tools：原子操作，比如读文件、写文件、执行终端命令、发 HTTP 请求。相当于手指头。
  5. Skills：多个工具加提示词、按固定流程封装好的“连招”。按技能键是 Tool，一套连招是 Skill。
  6. Planning：思考—行动—观察的循环，决定下一步调哪个工具、要不要重试。缺了它，前面五样就是散件。

4.2 术语对照表

以后看文档碰到这些词，直接对号入座：

你平时的说法 行业里的叫法 说明
上下文 Context Window / Working Memory / Short-term Memory 短期，跟着当前会话走
当前进行到哪一步 State Agent 循环里的状态
外部知识库 RAG / Long-term Memory / External Knowledge 长期，检索得来
读写文件、跑命令 Tools / Function Calling 原子能力
一套固定打法 Skills 工具的组合封装
自己想下一步 Planning / Agent Loop 自主循环

5. 顺着公式往深里挖

5.1 Planning：Agent 怎么“想事情”

  1. ReAct（Reasoning + Acting）：边想边做。想一步 → 调一个工具 → 看结果 → 再想。终端里那种 Agent 基本都是这个路子，好处是灵活，坏处是容易绕远。
  2. Plan-and-Execute：先一次性列好计划，再逐步执行。步骤清晰、可审计，但中途情况变了不太会随机应变。
  3. Reflection：执行完自己回头检查一遍，不对就重来。加点这个，正确率通常能拉上去一截，代价是多烧 token。

现实里的系统经常是混着用的：先 Plan 个大框架，具体每一步用 ReAct 跑，关键节点插一次 Reflection。

5.2 Tools：工具怎么被“调用”

模型本身不会执行代码，它只是输出一段结构化 JSON，说“我要调 read_file，参数是这个路径”。外层程序解析这段 JSON，真去读文件，再把结果塞回对话里。这套机制叫 Function Calling / Tool Use。

两个实际问题：

  1. 工具描述写得好不好，直接决定模型会不会用。描述就是工具的说明书，参数类型、取值范围都要说清。
  2. 工具太多会把上下文撑爆。现在的做法是按需加载——先只给模型一份工具清单，它要用哪个再加载哪个的完整定义。Anthropic 把这个叫 Tool Search，MCP 那边也有类似的 Programmatic Tool Calling。

5.3 Skills：从“按键”到“连招”，而且已经有标准了

Skill 是“工具 + 提示词 + 固定执行逻辑”打包好的一坨东西。比如“代码审查”这个 Skill，内部会依次读文件、按规则检查、生成报告，你只需要喊它一声。

值得记一笔的是：2025 年 12 月 Anthropic 把 Agent Skills 发布成了开放标准，2026 年也捐给了 Linux 基金会下的 AAIF。标准本身简单到离谱——一个 skill 就是一个文件夹，里面放一个 SKILL.md，写清楚这个技能干什么、什么时候用；需要的话再附脚本和参考材料。ChatGPT、Cursor、GitHub Copilot、VS Code 等 70 多个平台已经接了这套东西。

所以你用的 WorkBuddy 里那些 skill（/commit、各类文档技能），本质就是这种文件夹。

5.4 Memory：记忆其实分好几层

  1. 工作记忆：就在 Context Window 里，会话结束基本就没了。
  2. 情节/经验记忆：把过去做过的事、踩过的坑存下来，下次遇到类似的直接调。有些 Agent 框架会专门做这个。
  3. 语义记忆（RAG）：外部文档、代码库、知识库，检索着用。
  4. 参数记忆：模型训练时学到的东西，改不了，除非微调。

现在大家更爱说 Context Engineering（上下文工程），而不是 Prompt Engineering——因为真正决定效果的是“在这个有限的窗口里，该放什么、不该放什么、什么时候压缩”。

5.5 RAG：完整链路和适用边界

一次完整的 RAG：

文档切片 → 向量化 → 存向量库
用户提问 → 问题向量化 → 检索相似片段 → （可选）重排 → 连同问题喂给 LLM → 生成答案

什么时候别用 RAG：

  1. 资料量很小，直接全塞进上下文就行，没必要上向量库。
  2. 需要精确计算或严格推理的场景，检索来的片段反而干扰思路。
  3. 实时性要求极高、数据每毫秒都在变——检索索引跟不上。

6. Multi-Agent：从一个人到一个团队

6.1 为什么要上多个

单 Agent 有两个硬伤：context 一长，注意力就散；领域一杂，就容易在不懂的地方胡说。拆成多个专门的 Agent，各自带各自的工具和上下文，能并行就并行。

6.2 四种主流拓扑

模式 控制怎么走 适合 主要风险
Supervisor 一个主管分派任务、汇总结果， worker 干完把控制权交回 生产环境默认，任务能清晰拆分，要可审计 主管成瓶颈，它拆错了全队跟着错
Sequential Pipeline 固定顺序，A 的输出给 B，B 给 C 流程确定的多阶段活，比如草稿→检查→排版 没有并行；前面错了后面全废
Swarm / Handoff 没有主管，Agent 之间直接交接，谁擅长谁上 对话式路由、真正可并行的任务 难调试，容易陷入互相踢皮球的死循环
Blackboard 各 Agent 读写一块共享工作区，满足条件就上手 长时间异步、跨团队服务 工具链不成熟，控制逻辑复杂

还有两个常见的变体：

  • Hierarchical（层级）：主管上面还有主管，管一层层的团队。worker 超过五六个才值得加层，每加一层延迟和 token 都在涨。
  • Hybrid（混合）：现实系统基本都是混合的。最常见的是“主管 + 流水线”——主管决定走哪条流程，流程内部按固定步骤跑，兼顾灵活和可预测。

各框架的叫法不统一：LangGraph 叫 supervisor，CrewAI 叫 hierarchical process，OpenAI Agents SDK 叫 manager/handoff，本质都是同一套东西，别被名词绕进去。

flowchart LR
    U["用户任务"] --> S["主管 Agent<br/>拆解 + 分派"]
    S --> W1["检索员"]
    S --> W2["代码员"]
    S --> W3["测试员"]
    W1 --> M["汇总校验"]
    W2 --> M
    W3 --> M
    M --> S
    S --> R["最终交付"]

6.3 Agent 之间怎么说话

  1. 框架内部：靠消息传递和共享状态。handoff 时要把完整执行轨迹交过去，只传最后一条消息会丢掉中间的判断依据。
  2. 跨框架、跨厂商：靠 A2A（Agent2Agent）协议。Google 2025 年 4 月发布，6 月捐给 Linux 基金会，用 HTTP、SSE、JSON-RPC，靠 “Agent Card” 声明各自能力。

注意区分：MCP 管 Agent 怎么连工具和数据，A2A 管 Agent 怎么连别的 Agent。

6.4 代价和坑，比想象中大

  1. 烧钱：Anthropic 自己的数据，多 Agent 研究配置大约吃掉普通对话 15 倍的 token，单 Agent 同任务大约 4 倍。用在自己 API key 上，这个倍数直接变成账单。
  2. 上下文碎片化：各干各的，局部看都合理，合起来对不上。Cognition 那篇《Don’t Build Multi-Agents》举的例子是：一个子 Agent 画了超级马里奥风背景，另一个并行画了只风格不搭的鸟，主管拼不回去。
  3. 错误放大：交接点越多，错误传播越狠。有分析说没有明确拓扑的“agent 袋”比单个调教好的 Agent 错误率高得多，超过四五个 Agent 收益就开始被协调开销吃掉。
  4. 子任务互相依赖时反而更慢：多 Agent 的价值在并行。第三步必须拿到第二步的真实结果而不是摘要时（比如写代码），拆开就亏了。

6.5 什么时候别上

一个配好检索和几个工具的单 Agent，能覆盖大部分场景。上第二个 Agent 之前先问四个问题：

  1. 子任务真的能并行吗？
  2. 它们需要彼此的中间结果吗？
  3. 出错了能定位到哪个 Agent 吗？
  4. 多花的 token 换来什么可测的收益？

答不上来就别上。

7. MCP：工具的统一插座

7.1 它解决什么问题

没有 MCP 的时候，每个 AI 应用要为每个工具写一遍适配，N 个应用配 M 个工具就是 N×M 份代码。MCP 把这个变成 N+M：工具方按协议写一次 server，应用方按协议写一次 client。

官方的比喻是 USB-C：不管什么设备，插上就能用。

7.2 三个角色

  1. Host：AI 应用本体（Claude Code、VS Code、你自己的 Agent 程序），负责管权限、管授权、聚合上下文。
  2. Client：Host 为每一个 Server 创建一个 Client，一对一连接，负责传消息、维持安全边界。
  3. Server：暴露具体能力的小程序，可以是本地进程，也可以是远程服务。

一个关键设计：Server 看不到完整对话，也看不到别的 Server。 它只拿到自己需要的那点上下文，边界由 Host 把着。

7.3 三种原语

原语 作用 类比
Tools 可执行函数，AI 调了会真的做事（查数据库、改文件） 手
Resources 提供上下文的数据源（文件内容、数据库记录） 眼睛/资料
Prompts 可复用的提示词模板 话术模板

客户端这边还有一个 Elicitation，允许 Server 反过来向用户要信息或要确认。

7.4 底层和 2026 年的变化

  1. 消息格式是 JSON-RPC 2.0。
  2. 最新版规范（2026-07-28）改成无状态协议：每个请求自带版本号和能力声明，Server 可以独立处理，不用维护会话状态。
  3. 加了一个 server/discover 握手，Client 先问“你支持啥”，Server 声明能力，再按能力开放对应功能。
  4. Roots 和 Sampling 这两个客户端能力在 2026-07-28 版本里已弃用；新实现直接传路径参数、直接调模型 API，日志走 stderr 或 OpenTelemetry。
  5. 加了 Tasks 扩展，长任务返回一个句柄，Client 可以轮询结果。
  6. 工具变更支持通知推送，不用每次重新全量发现。

7.5 和 Function Calling、A2A 的区别

管什么 范围
Function Calling 模型怎么表达“我要调某个函数” 单个应用内部
MCP Agent 怎么连外部工具、数据、提示词 跨应用、跨语言的开放协议
A2A Agent 之间怎么发现彼此、交接任务 Agent 对 Agent

7.6 现状

  1. MCP 由 Anthropic 2024 年底推出，后来捐给了 Linux 基金会下的 Agentic AI Foundation（AAIF）。AAIF 由 Anthropic、Block、OpenAI 共同发起，Google、Microsoft、AWS、Cloudflare、Bloomberg 支持。
  2. 公开 MCP Server 超过一万个，ChatGPT、Cursor、Gemini、Copilot、VS Code 都接了。
  3. 主流语言都有官方 SDK，Python 和 TypeScript 的 SDK 月下载量过亿。
  4. Skill 标准也在同一个基金会里（见 4.3）。

8. 串回 DistriAgenda

这套东西落到毕设里，比较现实的用法：

  1. 开发期：用终端 Agent 干重复的活——批量改包名、补注释、找空指针、生成 CRUD 骨架。改完必须自己 review diff，别让它直接碰数据库迁移脚本。
  2. RAG 用得上：如果项目里要做“自然语言查日程/查任务”这类功能，RAG 比微调现实得多。先把数据结构和常用查询说明切成片段建索引，比让模型裸猜强。
  3. MCP 可以当加分项：毕设里做一个简化版 MCP Server，把日程查询能力暴露出去，让外部 AI 客户端能调。这个在答辩时比单纯 CRUD 有说服力，而且工作量不大。
  4. Multi-Agent 先别碰：毕设场景里任务依赖强、并行收益低，加多 Agent 只会让调试变地狱。单 Agent + 好工具 + 好上下文，够了。

9. 一页速查

  1. LLM = 脑子，只能说不能做。
  2. RAG = 开卷资料，解决“不知道”和“胡说”。
  3. Agent = LLM + 记忆 + 工具 + 技能 + 规划循环，能自己把活干完。
  4. Context Window / Working Memory = 短期记忆；RAG = 长期记忆。
  5. Tools = 原子按键；Skills = 连招；Planning = 自主循环。
  6. Multi-Agent = 团队，默认用 Supervisor，别一上来就 Swarm。
  7. MCP = Agent 接工具的统一插座；A2A = Agent 接 Agent 的协议。
  8. 判断要不要上复杂度：先问“并行收益是否大于协调成本”，大部分时候答案是否。
