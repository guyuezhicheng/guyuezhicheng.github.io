二、学术雷达 · 第 1 期（2026-11-10 检索）

今天这几条有个共同线索：让机器的输出能被机器检查。刚好和第一节 C 课对上，所以放前面讲。

1. Google DeepMind × Google Quantum AI：AI 发现并形式化验证量子程序

  • 出处：arXiv:2611.09822《Discovering formally verified quantum programs with AI》，v1 11-06、v2 11-09，PDF 日期 11-10；报道见 Agentic Tribune 2026-11-10。
  • 做了什么：用 Gemini 4 系列驱动的智能体团队，配合 Lean 定理证明器，从形式化规约生成量子程序，并给出机器可检查的正确性证明与资源上界证明。为此他们建了 Lean 量子程序库，含量子 Hoare 逻辑框架。
  • 报出来的数字（按论文写定的代价模型，Q·T = 逻辑量子比特数 × T 门数）：定点 arcsin 的 Q·T 成本降低 290× 以上；并行 Grover 搜索期望 oracle 轮数最多降 2.55×；聚变相关 stopping-power 模拟 10.9×，非 Born-Oppenheimer 分子动力学 8.08×，细胞色素 P450 能量计算 2.49×。
  • 防错机制值得记：多智能体团队共享一个版本化 wiki 存已验证结果与引理，还有跨团队“会议”交换想法；提交前由独立外部验证器在干净沙箱里对冻结规约重放，检查没有占位证明、代价定理能归约到声明的闭式结果。
  • 意义：AI 的角色从“生成看起来对的答案”挪到“生成带证明的结果”。更关键的是——这些电路大到经典机模拟不了、现有量子硬件也跑不动，形式化证明成了唯一能验证它的手段。这逼着整个领域把“正确性”写成可检查的规约，而不是靠跑一遍看看。
  • 别急着全信：这是 arXiv 预印本，结论建立在作者编码进 Lean 的规约与代价假设上，不是硬件实测；Lean 库与规约承诺“即将开源”，在外部复现之前按“有意思但待验证”处理。

2. Sketchpad：0.8B 小模型做出「任意长度都精确」的算术，还给了证明

  • 出处：arXiv:2611.04434《Sketchpad: certified exact arithmetic with a small vision-language model》，2026-11-03，cs.LG / cs.CL / cs.LO；代码 Apache 2.0。
  • 做了什么：Qwen3.5-0.8B 加一个低秩适配器，在一张“渲染出来的草稿纸”上执行算术过程。每次前向只看三格视野，吐出一个数字、一个进位/借位、以及下一步操作；固定的 runtime 负责移动视野，一个结果数字都不写。
  • 关键在证明：作者用 Lean 证明，只要每一步只读外部工作记忆的有界视野，那么“对任意输入长度都精确”就等价于“runtime 会呈现的有限视野集合上全对”；反过来，如果步骤还要读历史步骤，任何有限测试都不够。2,446 个视野在一台笔记本 GPU 的浏览器里全部通过。
  • 结果：任意长度有符号加减、长乘除、平方根、gcd；200/200 预注册题、220/220 千位加法与 20 位乘法全对（对照组最强的 GPT-6.1 Sol 是 217）。符号 runtime 用这些过程做多项式展开与因式分解；适配器上加个乘法门，不用草稿纸时能精确恢复基座模型。
  • 意义：老问题是“神经网络输出只是采样估的，没保证”。这篇没把计算外包给计算器（那是外挂），而是靠限制信息流 + 外部确定性 runtime + 形式化证明，把“无限长度上的正确性”压成有限个可检查的状态。模型还是那个模型，可验证性来自执行结构的设计。
  • 和今天的关系：三格视野 = 有界状态，固定 runtime = 控制流，一步一步读-写 = 确定性状态转移。这就是你今天要写的 C 程序。第一天就碰到这个心智模型很划算：以后看 KV Cache、看推理引擎的算子循环、看 Agent 的 while 循环，用的都是同一副眼镜。

3. 简讯：TCSExam 把“科研”做成可自动验算的考卷

  • 出处：arXiv:2611.07962，姚期智、杨植麟等，2026-11-05；科学网 11-09 报道。
  • 四条赛道：定理证明（Lean 4 内核逐行验算）、求解器工程（隐藏测试集跑可复用程序）、显式构造（交出对象 + 证书）、开放猜想。GPT-6 Astra 裸考 20 道定理证明做出 14 道；补中间引理后多个模型明显提分（Kimi K3 从 3 → 7，DeepSeek V4.1 Flash 从 0 → 6）。
  • 意义：评测从“答对题”转向“产出可被人类接着用的科研成果”；同时说明脚手架比堆参数更关键。你的错题本、每日检验、周日复盘，本质上就是给自己的脚手架。

今日雷达一句话：把正确性写成能被机器逐步检查的东西——论文里靠 Lean，程序里靠编译 + 确定的状态转移。这就是零基础第一门选 C 的理由。

四、新知：四个问题，逐个讲透

4.1 .c 怎么变成能跑的程序

四步，每步都有产物，别只记 gcc hello.c 一条命令：

步 干什么 命令 产物
1 预处理 展开 #include、替换宏、去掉注释 gcc -E hello.c -o hello.i hello.i（还是文本，可能几千行）
2 编译 把 C 翻译成汇编 gcc -S hello.i -o hello.s hello.s
3 汇编 汇编转成机器码目标文件 gcc -c hello.s -o hello.o hello.o（二进制，还不能跑）
4 链接 把 printf 的实现从 libc 接进来，定地址 gcc hello.o -o hello.exe hello.exe

为什么要分四步：报错位置能直接告诉你问题出在哪一层。#include 拼错 → 第 1 步就炸；语法错 → 第 2 步；undefined reference to ... → 第 4 步（函数声明有了、实现没接上）。以后调 PyTorch 的 C++ 扩展、调 ONNX Runtime，看到的还是这四类错。

4.2 hello.c 逐行拆

#include <stdio.h>          // 预处理：把 stdio.h 的内容原样插进来

int main(void) {            // 程序入口；void = 不接收命令行参数
    printf("hello, world\n");   // 调用库函数
    return 0;                   // 0 告诉操作系统"正常结束"
}
  • #include <stdio.h> 不是“导入 printf 的代码”，只是把 printf 的声明摆进来，让编译阶段能检查你传的参数对不对。真正的函数体在链接时从 libc 拿。
  • main 的返回值是给 shell 看的，不是给 printf 看的。跑完用 echo $?（Git Bash）能看到 0。
  • \n 是换行符，一个字符，不是两个。

4.3 变量到底是什么

一句话：一块有名字、有大小、有地址的内存。C 不帮你藏这三层。

  • 大小 → sizeof(类型)，单位是字节。
  • 地址 → &变量，用 %p 打印（要强转 (void *)）。
  • 值 → 那块内存里当前的比特按类型解释出来的结果。

sizeof 的结果不是标准写死的。标准只规定各类型的最小取值范围和相对大小关系，具体字节数由平台和 ABI（数据模型）决定：64 位 Linux 是 LP64（long/指针 8 字节），64 位 Windows 是 LLP64（long 仍 4 字节、指针 8 字节）。所以今天你必须在自己机器上实测，不许背答案。

4.4 为什么第一门是 C（不是 Python）

Python 里 a = [1, 2, 3] 之后，内存怎么排、什么时候回收、为什么 b = a 会联动，全被运行时包住了。C 里 int a = 42; 就是“在栈上划 4 字节，写入 42”，没有第二层解释。先把这层看透，后面学 C++ 的 RAII、NumPy 的 stride、JVM 的堆分区、模型量化里的字节数，才有地方挂。今天学术雷达那两篇论文，靠的也是同一件事：状态可见、转移确定，才谈得上验证。

#include <stdio.h>

int main(void) {

跑四步编译，每一步都用 ls -l 看一眼产物大小，再用 head -n 20 hello.i 感受一下头文件展开了多少行：

gcc -E hello.c -o hello.i
gcc -S hello.i -o hello.s
gcc -c hello.s -o hello.o
gcc    hello.o -o hello.exe
./hello.exe

练习 2：probe.c —— 把内存看清楚

#include <stdio.h>

int global_x = 10;

int main(void) {
    int a = 42;
    double b = 3.14;
    char c = 'A';
    int arr[4] = {1, 2, 3, 4};

    printf("== 类型大小（字节）==\n");
    printf("char      : %zu\n", sizeof(char));
    printf("short     : %zu\n", sizeof(short));
    printf("int       : %zu\n", sizeof(int));
    printf("long      : %zu\n", sizeof(long));
    printf("long long : %zu\n", sizeof(long long));
    printf("float     : %zu\n", sizeof(float));
    printf("double    : %zu\n", sizeof(double));
    printf("void*     : %zu\n", sizeof(void *));

    printf("\n== 地址 ==\n");
    printf("&a        : %p\n", (void *)&a);
    printf("&b        : %p\n", (void *)&b);
    printf("&c        : %p\n", (void *)&c);
    printf("&global_x : %p\n", (void *)&global_x);
    printf("arr       : %p\n", (void *)arr);
    printf("&arr[0]   : %p\n", (void *)&arr[0]);
    printf("&arr[1]   : %p\n", (void *)&arr[1]);
    printf("相邻 int 间隔: %td 字节\n", (char *)&arr[1] - (char *)&arr[0]);

    return 0;
}
gcc -std=c11 -Wall -Wextra probe.c -o probe.exe && ./probe.exe

要求：把输出抄进笔记，标出三件事——① 哪个类型最大；② 指针宽度是几；③ &global_x 和 &a 的地址是不是明显不在一个量级（是，一个在全局区、一个在栈上；W2 会画完整内存图）。

练习 3：故意写错，学会读报错

新建 bad.c：

#include <stdio.h>

int main(void) {
    printf("%d\n", "not a number")
    return 0;
}
gcc -std=c11 -Wall -Wextra bad.c -o bad.exe

读报错，在笔记里写清：① 编译器报在第几行；② 缺了什么；③ 就算补上分号，-Wformat 那条警告在说什么。然后修好它、重新编译。读报错是今天最值钱的练习，后面 26 周天天要用。

七、检验标准（5 条，逐条打勾，不许“大概懂了”）

# 检验 判分要点
1 不看资料默写 hello.c 并编译运行通过 能一次写对 #include、main、return 0；输出正确
2 说出本机 sizeof(int) 的值及理由 说出具体数字 + “由平台 ABI 决定，标准只规定最小范围”；能指出自己机器是 LP64 还是 LLP64
3 解释 #include <stdio.h> 到底做了什么 答到“预处理阶段文本插入声明，供编译期做类型检查；实现在链接阶段从 libc 来”
4 说出编译四步各产出什么文件，并指出 undefined reference 出在哪一步 四步产物齐全；答“链接阶段”
5 独立读懂一条 gcc 报错并定位修复 能指出行号、错误类别、修法；-Wformat 警告能说清是格式符与实参类型不匹配

5 条全过 → 明天进 D2。任一不过，明天先补，不学新内容。
