2.1 Compositional Symbolic Execution à la Carte：把内存模型做成可组合部件

  1. 出处：arXiv:2611.31692，v1 2026-11-23，cs.PL；扩展版，对应 POPL’27 论文（abs 页 comments 标注）。6 作者：Sacha-Élie Ayoun、Andreas Lööw、Seung Hoon Park、Opale Sjöstedt、Petar Maksimović、Philippa Gardner。abs 页未逐作者印机构，不臆断。预印本，未经同行评审、待复现。
  2. 做了什么：提出“组合式符号执行 à la carte”——用组合器（combinator）方式搭建符号执行工具的关键部件：内存模型、用户自定义谓词的管理与自动化、双归纳（bi-abductive）分析。元理论在 Rocq 证明助手里机制化，目标是让工具开发者以最小实现和证明代价、按构造正确（correct-by-construction）地搭出针对任意语言的符号执行工具。在 Gillian 上实现，覆盖 C、JavaScript、Rust 各自内存模型的细节，跑通既有 case study，无意外行为、性能相当。
  3. 改变了哪个旧假设：推翻“给一门语言做符号执行就得从零手写一套引擎”。内存模型、谓词、分析都能拆成可组合模块，换语言/换内存模型只换部件。
  4. 意义：把程序分析从“手工艺”推向“按构造正确 + 可组合”，C/Rust/JS 的内存语义能被同一套框架描述和推理。
  5. 关联今天：栈帧就是“函数调用这一层的内存模型”——参数、返回地址、局部变量怎么摆，正是符号执行必须建模的最小单元。你今天用 GDB 在实例层看一个具体栈帧，这篇在抽象层把栈/堆内存模型做成可组合、可证明的对象。GDB 的 x 看的是某一帧某块内存的真实字节，符号执行建模的是这类内存的一般规律；对着同一件事，一个动手看、一个动脑证。

2.2 FerroScope：跨层取证诊断 C→Rust 性能，别只看源码

  1. 出处：arXiv:2611.33490，v1 2026-11-24，cs.PF / cs.PL / cs.SE；3 作者：Dalton Davis、Kunal Pai、Tapti Palit。abs 页未印机构，不臆断。预印本，未经同行评审、待复现；数字为作者在论文中的实测报告。
  2. 做了什么：先对 12 组“C 实现 + 对应 Rust 实现”做跨层刻画，发现运行时安全检查并不必然主导开销——编译器优化与微架构常常抵消其成本，12 组中 8 组至少有一个 Rust 实现落在 C 的 10% 以内、甚至更快。据此做 FerroScope：把源码级分析、编译器优化 remarks、动态指令 trace、硬件性能计数器四层证据合成，诊断 C/Rust 性能差异，能指出“被冗余边界检查抑制住的编译器优化”。再用一个 LLVM pass 通过 guarded loop versioning 把冗余边界检查外提、保留 Rust panic 语义，Selection Sort 相对 C 的开销从 2.95× 降到 1.00×，Merge Sort 从 1.43× 降到 0.91×。
  3. 改变了哪个旧假设：推翻“Rust 的安全检查天然比 C 慢”和“性能差异看源码层就够了”。真实开销来自多层交互，必须把源码、编译器决定、实际执行的指令对齐着看。
  4. 意义：性能诊断要跨层取证；一个看似无害的边界检查会通过抑制下游优化放大代价，修法要落到编译器 pass 才彻底。
  5. 关联今天：你今天用 bt/info frame/x 单步看栈，就是跨层取证的手动版——源码行、机器指令、寄存器/内存、调用栈对齐着看。这篇把同一思路工程化：不只盯 C 源码，还看编译器 remark 和指令 trace。它还解释了一个调试铁律：为什么必须 -g -O0 编译再调试——开了优化，源码行与实际指令对不上、局部变量被优化掉、栈帧可能被内联打通，GDB 看到的世界就不真实了。这正是 2.1 那篇“内存模型/行为要被正确建模”的反面警示。

3. 新知讲解：栈帧、函数调用约定、GDB 单步

3.1 栈在哪，帧是什么（承接 D10）

  1. 进程地址空间里，栈（stack）从高地址往低地址长；每调用一个函数，就在栈顶往低地址方向压一块，叫栈帧（stack frame）；函数返回，这块被弹出。编译器自动管理，分配释放就是改寄存器，极快。
  2. 两个寄存器是锚点（x86-64 叫 rsp/rbp，x86-32 叫 esp/ebp）：
    • rsp/esp（栈指针）：永远指向当前栈顶（最低的有效地址）。压栈/弹栈就是改它。
    • rbp/ebp（帧指针）：固定指向当前帧的某个位置，函数执行期间不变。访问参数 rbp+8、rbp+16…，访问局部变量 rbp-4、rbp-8…，偏移稳定，调试器靠它还原帧。
  3. 栈往低地址长意味着：新帧的地址比旧帧小。递归时每深一层，帧地址就更小一截——这正是 3.5 里 min.c 打印 &n 逐层递减能看到的现象。

3.2 一个栈帧里装什么

  1. 参数：调用者按约定把参数准备好，能用寄存器就用寄存器；装不下或需要地址的，放到栈上（帧里）。
  2. 返回地址：call 指令自动把“下一条指令的地址”压进栈。函数 ret 时取出来跳回去。它是调用链的“绳结”，bt 就是顺着它一串串找回调用者的。
  3. 保存的寄存器：被调用者若要用某些” callee-saved “寄存器（x86-64 System V 里 rbx、rbp、r12–r15），得先存进帧、返回前恢复，否则会破坏调用者的值。
  4. 局部变量：函数里声明的自动变量，挨着放在帧里。关掉优化（-O0）时它们老老实实待在栈上，GDB 才能 info locals 看到；开了优化可能被塞进寄存器甚至算掉。
  5. 一帧的典型布局（地址从高到低）：调用者的帧 → 参数（≥7 个的部分）→ 返回地址 → 保存的 rbp → 保存的 callee-saved 寄存器 → 局部变量 → 栈上临时/对齐填充 → 当前 rsp。具体顺序随 ABI 和编译器变，别死记，记住“这几种东西都在帧里”。

3.3 调用约定：两块代码凭什么能互相调用

  1. 调用约定（calling convention）是 ABI 的一部分，规定四件事：参数放哪、返回值放哪、谁清理栈、哪些寄存器调用者/被调用者各管各的。没有它，不同编译器、不同模块、不同语言编出来的代码就没法互调。
  2. 主流 x86-64 约定对比：
    • System V AMD64（Linux/macOS）：整数/指针参数依次走 rdi, rsi, rdx, rcx, r8, r9，返回值 rax；浮点走 xmm0–xmm7。
    • Microsoft x64（Windows）：整数/指针参数依次走 rcx, rdx, r8, r9，返回值 rax；还要在调用前预留 32 字节 shadow space。
  3. 调用者保存（caller-saved） vs 被调用者保存（callee-saved）：约定里划分了两拨寄存器。caller-saved 的，调用者不保证还在，要用自己存；callee-saved 的，被调函数用前必须存、返回前必须恢复。这条规则是 3.2”保存的寄存器“的由来。
  4. 为什么必须对齐：D57 用 ctypes/pybind11 让 Python 调 C++、D117 用 C# P/Invoke 调 C++ 矩阵乘，全靠双方按同一 ABI 生成代码。约定不一致（参数顺序、栈清理方、结构体布局）就是静默的错误结果或崩溃——比编译错误更难查。
  5. 眼见为实：gcc -S -O0 day19/frames.c -o frames.s，找到 fact 函数，看调用前参数怎么进寄存器、call fact 前后 rsp 怎么变、帧里怎么 push/mov。这是练习 5。

3.4 递归 = 一层层压帧

  1. 递归不是“魔法地调用自己”，就是每层调用各压一个新帧，各有自己的参数 n、局部变量 r/marker，互不干扰。这就是 D4”fib(4) 调用树“在栈上的真实样子：树的一个节点 = 栈上的一帧。
  2. 栈深度 = 递归层数 × 每帧大小。层数太多（无基例或 n 巨大）就把栈耗尽 → 栈溢出（stack overflow）→ SIGSEGV。练习 4 的 oob 与这条相呼应：越界写和栈耗尽都是“碰了不该碰的栈内存”。
  3. 一层帧的地址比上一层小，min.c 打印的 &n 会逐层递减，可以肉眼验证“栈往低地址长”。

3.5 GDB 单步三板斧

  1. 编译必须带 -g -O0：-g 保留符号和源码行号，-O0 关优化保证帧和变量真实（呼应 2.2）。gcc -std=c11 -Wall -Wextra -g -O0 day19/frames.c -o day19/frames。
  2. 起手：gdb -q ./day19/frames → (gdb) break fact → (gdb) run 4 → 停在断点。break b 可写函数名或行号；run 后带的是程序参数。
  3. 三种走法：next（n，不进函数，把函数调用当一步）、step（s，进函数内部）、finish（跑完当前函数停在返回处）。continue（c）跑到下一个断点。
  4. 看现场：bt（backtrace）打印整条调用链，#0 是栈顶（当前正在执行的帧），数字越大越靠上层调用者；frame N 切到第 N 帧；info frame 看该帧详细信息（帧基址、返回地址、上一级帧）；info locals 列局部变量；info args 列参数；p 变量 打印值；x/4xw 地址 按 4 个 4 字节十六进制看原始内存（x 的 4 个数、x 十六进制、w 字长 4 字节，可换 b/h/g 和 d/u/c/s）。
  5. 崩溃定位流程：程序 SIGSEGV 停下后 → bt 看崩在哪个函数（哪帧）→ frame 0 看崩溃帧 → info locals/info args/p 找出哪个指针是 NULL、哪个下标越界 → 需要的话 frame 1、frame 2 往调用者查参数从哪来。关键：崩的帧（#0）常常不是犯错的那帧——越界写可能早几帧发生，到某一帧才踩到非法地址触发崩溃。这就是检验标准 3 要问的。

3.6 最小示例代码（day19/min.c，完整可直接编译）

一份文件把栈帧地址、按值传递、递归逐层压帧跑一遍；讲义代码块与落盘文件逐字一致。

/* day19/min.c - 最小示例：栈帧地址 + 按值传递 + 递归每层一帧
 * 编译: gcc -std=c11 -Wall -Wextra -g -O0 day19/min.c -o day19/min
 * 运行: ./day19/min   (Windows: day19\min.exe)
 */
#include <stdio.h>

/* 单层栈帧：参数 n、局部变量 local 都落在这一帧的栈地址上 */
static void frame_once(int n)
{
    int local = n * 10;
    printf("frame_once: n=%d &n=%p local=%d &local=%p\n",
           n, (void *)&n, local, (void *)&local);
}

/* 按值传递：改形参动不了实参 */
static void add_one(int x)
{
    x = x + 1;
    printf("add_one:    x=%d &x=%p\n", x, (void *)&x);
}

/* 递归：每层各有一份 n 和 marker，地址随帧一层层往下走 */
static void recurse(int n)
{
    int marker = n;
    printf("recurse:    n=%d &n=%p &marker=%p\n",
           n, (void *)&n, (void *)&marker);
    if (n > 0) {
        recurse(n - 1);
    }
}

int main(void)
{
    int a = 5;
    printf("main:       a=%d &a=%p\n", a, (void *)&a);
    frame_once(a);
    add_one(a);
    printf("after add_one: a=%d (unchanged)\n", a);
    printf("--- recursion ---\n");
    recurse(3);
    return 0;
}

编译运行：gcc -std=c11 -Wall -Wextra -g -O0 day19/min.c -o day19/min && day19/min

期望输出（9 行；地址是运行时值，每次不同，只看规律，别背数字）：

main:       a=5 &a=0x........
frame_once: n=5 &n=0x........ local=50 &local=0x........
add_one:    x=6 &x=0x........
after add_one: a=5 (unchanged)
--- recursion ---
recurse:    n=3 &n=0x........ &marker=0x........
recurse:    n=2 &n=0x........ &marker=0x........
recurse:    n=1 &n=0x........ &marker=0x........
recurse:    n=0 &n=0x........ &marker=0x........

逐行读：add_one 里 x 变成 6，但回到 main 后 a 还是 5——这就是 D4 的值传递，形参 x 在自己帧里，&x 和 &a 也不同；recurse 四行的 &n、&marker 一层比一层小，证明栈往低地址长、每层各有一份变量。

4. 练习（动手，当场跑通）

说明：本机无 gcc/gdb（CMake 因找不到 C 编译器配置失败），命令请在装了 GCC + GDB 的环境执行；讲义里的 C 代码已用 pycparser 做过 C11 语法校验。

  1. 最小示例：gcc -std=c11 -Wall -Wextra -g -O0 day19/min.c -o day19/min && day19/min，确认 3.6 的 9 行；盖住代码，用自己的话讲清：为什么 add_one 改不了 a、&n 为什么逐层递减。
  2. 递归单步：gcc -std=c11 -Wall -Wextra -g -O0 day19/frames.c -o day19/frames，然后 gdb -q ./day19/frames：break fact → run 4 → 每次 bt 看调用链长了几层 → info frame 看当前帧 → info locals/p n 看本层变量 → 用 step 进递归、next 跳过、finish 返回上层。记录 fact(4) 四层各自的 n 与帧地址。
  3. 崩溃定位（空指针）：gcc -std=c11 -Wall -Wextra -g -O0 day19/traps.c -o day19/traps，gdb -q ./day19/traps → run null → 崩在 SIGSEGV → bt（看 #0 是哪帧）→ frame 0 → info locals → info args → p p（看到 p 是 NULL）→ x/4xw p（NULL 地址读不出，符合预期）。写下“崩在第几帧、哪个函数、哪个变量是 NULL”。
  4. 崩溃定位（越界）：gdb -q ./day19/traps → run oob → bt → frame 0 → info args → p idx（1000000）→ p buf → x/4xw buf（1 2 3 4）。指出越界下标是谁、写到了哪；讨论：如果 -O2 编译，info locals 还能看到这些变量吗？（回看 2.2）
  5. 看汇编验证调用约定：gcc -S -O0 day19/frames.c -o frames.s，打开 frames.s 找到 fact: 标签，圈出 call fact 那一行，看参数进哪个寄存器、call 前后 rsp 怎么变、pushq/movq 都存了什么。答不出“参数走哪个寄存器”就回看 3.3。

5. 产出清单（必须落盘）

  1. day19/min.c — 最小示例（已落盘，讲义 3.6 代码块与它逐字一致）。

  4. day19/gdb.md — 课表硬产出：你自己写，至少两段完整 GDB 会话记录（frames 递归断点一段、traps null 或 oob 崩溃一段），每段含输入命令与真实输出，明确标出“崩溃在第几帧、哪个函数、哪个变量越界/NULL”。
  5. day19/stack_diagram.md — 手绘或文本画 fact(4) 的调用栈：4 层帧，每层标相对地址、n、r、返回地址指向谁；画清栈往低地址长。
  6. day19/frames.s — 第 5 题的汇编产物，并在文件末尾用注释写“参数走哪个寄存器、call 如何压返回地址”。

6. 检验标准（5 条硬条件，逐条能回答“过没过”）

  1. day19/min.c 编译零 error，./day19/min 输出讲义 3.6 的 9 行（地址值忽略）：add_one 后 a 仍为 5、recurse 共 4 层且 &n 逐层递减。少一层、对不上或说不出这两点 = 不过。
  2. 不看资料讲清栈帧四要素（参数 / 返回地址 / 保存的寄存器 / 局部变量）、rsp 与 rbp 的分工、栈为何往低地址长；说清一次 call/ret 如何压帧弹帧。少一样或说反方向 = 不过。
  3. 用 GDB 跑 traps null：能报出“崩溃在 #0 帧、deepest_null 函数、指针 p 为 NULL”，并说清“崩的帧 #0 不一定是错误的帧（越界/错误可能更早发生）”。报错帧号或变量、答不出这句 = 不过。
  4. 用 GDB 跑 frames 4：bt 显示的递归层数与 n=4 一致，能演示 step 进函数、next 不进、finish 返回上层，info locals/p n 看到当前帧变量。做不出或分不清 step/next = 不过。
  5. day19/gdb.md 含至少两段完整命令+真实输出、day19/stack_diagram.md 画出 4 层栈帧、day19/frames.s 有汇编与注释，git log -1 看得到当日 commit；第 5 节第 9 项补档清单逐项有产出或明确缺口记录。缺一项 = 不过。
